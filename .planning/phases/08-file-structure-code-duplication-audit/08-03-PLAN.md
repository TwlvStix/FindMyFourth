**Audit Context:**
- Architecture: Feature-layered Clean Architecture with Provider state management
- Expected Layers: Entry Point → UI (Widgets) → State (Providers) → Service (Business Logic) → Data (Backend/Firestore)
- Pattern: Widgets use Providers, Providers wrap Services, Services use Backend queries
- 170 Dart files to analyze for layer violations

**Architectural Patterns (from ARCHITECTURE.md):**
- **UI Layer**: Widgets/Screens in lib/main_function/, lib/profile/, lib/chat_group/, etc.
  - Should: Display UI, handle user interaction, use Provider.of() or context.watch()
  - Should NOT: Make Firestore queries directly, contain business logic, manage auth state
- **State Layer**: Providers in lib/providers/
  - Should: Wrap services, cache data, notify listeners
  - Should NOT: Contain business logic, make Firestore queries (delegate to services)
- **Service Layer**: Services in lib/services/
  - Should: Business logic, Firestore operations, transactions
  - Should NOT: UI code, Provider logic, direct widget interaction
- **Data Layer**: Backend queries in lib/backend/backend.dart, Records in lib/backend/schema/
  - Should: Firestore query functions, serialization
  - Should NOT: Business logic, UI code, Provider state

**Known Concerns (from CONCERNS.md):**
- ChatService has complex transaction logic (fragile but properly placed)
- UserProvider has caching with StreamRequestManager (correct pattern)
- No tests exist - can't verify separation through test boundaries

**Target Violations:**
- Widgets making Firestore queries directly (bypassing service layer)
- Business logic in widgets (should be in services)
- UI code in services (should be in widgets)
- Providers containing business logic (should delegate to services)
- Models vs Records confusion (domain models should not import Firestore)
</context>
