# Plan 01-01: Audit existing design tokens and component library

**Goal**: Catalog all existing design tokens (colors, typography, spacing) and reusable components to understand what already exists and identify gaps or inconsistencies.

**Context**: The app has a foundation of design tokens in `lib/core/design_tokens/` and reusable components in `lib/core/widgets/`, but they're inconsistently applied across the 136 Dart files. This audit will create a comprehensive inventory.

**Success criteria**:
- Complete inventory of all design tokens (colors, typography, spacing scales)
- Complete inventory of all reusable components with their variants
- Documentation of what exists vs what's needed for consistency
- Clear understanding of current usage patterns

**Dependencies**: None (first plan in phase)

## Tasks

<task id="01-01-01" type="discover" wave="1">
  <description>Audit design token files and document all available tokens</description>
  <instructions>
1. Read all files in `lib/core/design_tokens/`:
   - `colors.dart` - Document all color tokens and their usage
   - `typography.dart` - Document all text styles and font configurations
   - `spacing.dart` - Document spacing scale and layout tokens

2. Create `.planning/phases/01-foundation-audit/design-tokens-inventory.md` with:
   - Complete list of all color tokens (primary, secondary, semantic, etc.)
   - Complete list of all typography styles (headings, body, labels)
   - Complete list of all spacing tokens (margin/padding scales)
   - Notes on any missing or incomplete token categories

3. Document observations about token organization and naming consistency
  </instructions>
  <rationale>Understanding what design tokens exist is the foundation for identifying inconsistencies</rationale>
</task>

<task id="01-01-02" type="discover" wave="1">
  <description>Audit component library and document all reusable components</description>
  <instructions>
1. Read all widget files in `lib/core/widgets/`:
   - Use Glob to find all files: `lib/core/widgets/**/*.dart`
   - Document each component with its variants and props

2. Create `.planning/phases/01-foundation-audit/component-library-inventory.md` with:
   - Complete list of all reusable components (AppButton, AppCard, AppDropDown, etc.)
   - For each component, document:
     - Available variants (primary, secondary, etc.)
     - Configuration options (size, color, style)
     - Current usage patterns
   - Note any components that lack variants or have inconsistent APIs

3. Identify common UI patterns that should have components but don't
  </instructions>
  <rationale>Knowing which reusable components exist helps identify where widgets are reinventing the wheel</rationale>
</task>

<task id="01-01-03" type="discover" wave="2">
  <description>Analyze component usage patterns across key screens</description>
  <instructions>
1. Sample 10-15 representative widget files from key areas:
   - Game screens: `games_list_widget.dart`, `create_game_widget.dart`, `game_joined_detailed_widget.dart`
   - Social: `golfers_widget.dart`, `community_widget.dart`, `tab_friends_widget.dart`
   - Profile: `main_profile_widget.dart`, `edit_profile_widget.dart`
   - Chat: `chat_widget.dart`, `game_chat_details_widget.dart`

2. For each file, note:
   - Which reusable components from `lib/core/widgets/` are used
   - Where custom UI is built instead of using components
   - Patterns that repeat across multiple files
   - Inconsistencies in how similar elements are styled

3. Add findings to `.planning/phases/01-foundation-audit/component-library-inventory.md` under "Usage Patterns" section
  </instructions>
  <depends_on>01-01-02</depends_on>
  <rationale>Understanding how components are actually used (or not used) reveals adoption gaps</rationale>
</task>

<task id="01-01-04" type="document" wave="3">
  <description>Create design system gaps report</description>
  <instructions>
1. Synthesize findings from design tokens and component audits

2. Create `.planning/phases/01-foundation-audit/design-system-gaps.md` with:

   **Token Gaps:**
   - Missing or incomplete token categories
   - Tokens that exist but aren't used consistently
   - Hardcoded values that should be tokens

   **Component Gaps:**
   - Common UI patterns without reusable components
   - Components that exist but lack needed variants
   - Inconsistent component APIs

   **Priority Assessment:**
   - Rank gaps by impact on consistency
   - Note which gaps block standardization work

3. Include specific examples with file paths and line numbers where relevant
  </instructions>
  <depends_on>01-01-01,01-01-02,01-01-03</depends_on>
  <rationale>Clear gap analysis informs Phase 2 component standardization work</rationale>
</task>
