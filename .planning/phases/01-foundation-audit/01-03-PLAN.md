# Plan 01-03: Create standardization roadmap with priority areas

**Goal**: Synthesize audit findings from Plans 01-01 and 01-02 into a concrete, prioritized standardization roadmap that guides Phase 2-5 execution.

**Context**: After auditing design tokens, components, and screen inconsistencies, we need to organize findings into actionable work packages. This plan creates the "how we'll fix it" strategy based on the "what's wrong" from the audits.

**Success criteria**:
- Clear priority order for standardization work (which components/patterns first)
- Specific action items mapped to Phases 2-5
- Dependencies and sequencing identified (what must be fixed before what)
- Success metrics defined for each standardization area
- Quick wins identified vs longer-term refactoring

**Dependencies**: Plans 01-01 and 01-02 must complete first

## Tasks

<task id="01-03-01" type="plan" wave="1">
  <description>Synthesize audit findings into standardization themes</description>
  <instructions>
1. Read all audit documentation from Plans 01-01 and 01-02:
   - Design tokens inventory
   - Component library inventory
   - Design system gaps report
   - Spacing inconsistencies
   - Typography inconsistencies
   - Component inconsistencies
   - Navigation inconsistencies
   - Inconsistency priority report

2. Identify standardization themes that group related issues:
   - Example: "Button standardization" (covers component variants + spacing + consistent styling)
   - Example: "Card layout standardization" (covers spacing + typography + visual style)
   - Example: "Input field consistency" (covers component API + validation styling + spacing)

3. Create `.planning/phases/01-foundation-audit/standardization-themes.md` with:
   - 8-12 major standardization themes
   - For each theme:
     - Issues it addresses (with file path references)
     - Affected screens/features
     - Current state vs desired state
     - Complexity estimate (simple, moderate, complex)
  </instructions>
  <depends_on>01-01-04,01-02-05</depends_on>
  <rationale>Grouping issues into themes creates manageable work packages</rationale>
</task>

<task id="01-03-02" type="plan" wave="2">
  <description>Map standardization themes to Phase 2-5 execution sequence</description>
  <instructions>
1. Review the Phase 2-5 goals from ROADMAP.md:
   - Phase 2: Component Library Standardization (4 plans)
   - Phase 3: Typography System (3 plans)
   - Phase 4: Spacing System (3 plans)
   - Phase 5: Screen Flow Polish (3 plans)

2. Map each standardization theme to appropriate phase(s):
   - Component themes → Phase 2
   - Typography themes → Phase 3
   - Spacing themes → Phase 4
   - Navigation themes → Phase 5

3. Within each phase, suggest execution order based on:
   - Dependencies (fix foundational components first)
   - Impact (highest visible impact first)
   - Complexity (quick wins early to build momentum)

4. Create `.planning/phases/01-foundation-audit/phase-execution-sequence.md` with:
   - For each of Phases 2-5:
     - Recommended order of standardization themes
     - Rationale for sequencing
     - Dependencies between themes
     - Expected outcomes after each theme
  </instructions>
  <depends_on>01-03-01</depends_on>
  <rationale>Clear sequencing prevents rework and ensures dependencies are respected</rationale>
</task>

<task id="01-03-03" type="plan" wave="2">
  <description>Identify quick wins and foundational work</description>
  <instructions>
1. From the standardization themes, identify:

   **Quick Wins (1-2 hours each):**
   - High visibility, low complexity fixes
   - Example: Standardize all primary button instances to use AppButton
   - Example: Replace hardcoded heading styles with typography tokens

   **Foundational Work (must happen early):**
   - Changes that other work depends on
   - Example: Complete AppButton variants before standardizing all button usage
   - Example: Define typography hierarchy before applying across screens

2. Create `.planning/phases/01-foundation-audit/quick-wins-and-foundations.md` with:
   - List of 5-8 quick wins with file paths and specific changes
   - List of 3-5 foundational items that must happen first
   - For each item:
     - Effort estimate
     - Impact assessment
     - Which phase it belongs to
     - What it unblocks
  </instructions>
  <depends_on>01-03-01</depends_on>
  <rationale>Quick wins build momentum; identifying foundations prevents blocking issues</rationale>
</task>

<task id="01-03-04" type="plan" wave="3">
  <description>Define success metrics for standardization work</description>
  <instructions>
1. For each standardization theme, define measurable success criteria:
   - Quantitative: "All 47 primary action buttons use AppButton with consistent variant"
   - Quantitative: "Hardcoded spacing values reduced from 203 to <20"
   - Qualitative: "Screen titles use consistent typography hierarchy"
   - Qualitative: "Navigation transitions feel smooth and predictable"

2. Define phase-level success metrics:
   - Phase 2 completion: "All components have documented variants, 90% usage adoption"
   - Phase 3 completion: "Typography tokens used consistently, <5 hardcoded text styles"
   - Phase 4 completion: "Spacing tokens used throughout, harmonious layouts"
   - Phase 5 completion: "Consistent transitions, polished key flows"

3. Create `.planning/phases/01-foundation-audit/success-metrics.md` with:
   - Theme-level metrics
   - Phase-level metrics
   - Overall project success criteria
   - How to measure/verify each metric
  </instructions>
  <depends_on>01-03-01,01-03-02</depends_on>
  <rationale>Clear metrics ensure we know when standardization work is complete</rationale>
</task>

## Checkpoints

### Mid-execution (after task 01-03-03)
**Purpose**: Verify planning approach is sound before final documentation

**Check**:
- Standardization themes comprehensively cover audit findings
- Phase mapping aligns with ROADMAP.md phase goals
- Quick wins are genuinely quick and high-impact
- Foundational work is correctly identified as blocking

**If issues found**: Revise themes or sequencing before creating final roadmap

### Pre-commit (after task 01-03-05)
**Purpose**: Ensure roadmap is actionable and complete

**Check**:
- Standardization roadmap is clear and comprehensive
- Execution sequence is logical with dependencies respected
- Success metrics are specific and measurable
- Document provides clear guidance for Phase 2-5 planning
- Quick wins and foundations are well-defined

**If issues found**: Refine roadmap document to address gaps

## Notes

- This plan synthesizes findings - no new discovery work
- The roadmap should be pragmatic and achievable
- Balance quick wins with deeper refactoring
- Consider technical constraints (large widgets that can't be fully refactored immediately)
- The roadmap may suggest adjustments to Phase 2-5 plans based on findings
- Success metrics should be realistic, not perfectionistic
- Document should be readable by future developers or stakeholders
- This completes Phase 1 and sets up Phase 2 execution
