<task type="auto">
  <name>Task 2: Identify denormalization patterns and data duplication</name>
  <files>.planning/phases/09-data-model-schema-audit/SCHEMA-DESIGN-AUDIT.md</files>
  <action>
    **Audit denormalization strategy:**
    1. **Intentional denormalization** (performance optimization):
       - Chat last_message stored in chats collection
       - Game joined_players count vs array length
       - User last_active_time for online status
       - Identify which patterns are well-designed vs problematic

    2. **Unintentional data duplication** (maintainability risk):
       - User name fields (first_name/last_name vs display_name)
       - Game date vs created_time timestamp confusion
       - Course data duplicated in games (coursePlay String vs courseRef)
       - Chat users array vs memberIds array (legacy migration incomplete)

    3. **Missing denormalization** (N+1 query risks):
       - Game host user info not denormalized (requires user lookup)
       - Chat participant names not cached (requires 2-N user lookups per chat)
       - Friend request sender/receiver info requires lookups

    4. **Stale data risks**:
       - Which denormalized fields need update triggers?
       - Are there Cloud Functions maintaining consistency?
       - Document which patterns rely on manual synchronization

    **Document patterns with:**
    - Pattern ID (S-DENORM-001, S-DENORM-002...)
    - Collections/fields involved
    - Read vs write tradeoff analysis
    - Consistency maintenance strategy (triggers, manual, none)
    - Stale data risk assessment
    - Recommendation (keep, fix sync, normalize, denormalize more)

    **Reference Phase 8 findings:**
    - Direct Firestore access (16 violations) may bypass denormalization updates
    - Provider caching patterns vs Firestore denormalization strategy
  </action>
