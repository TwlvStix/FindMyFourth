       - `games.joined_players[]` → `users/{uid}` (participants, List<DocumentReference>)
       - `games.courseRef` → `course/{id}` (course info, DocumentReference)
       - `games.chatRef` → `chats/{id}` (game chat, DocumentReference)
       - **Inconsistency alert**: Both `userRef` (DocumentReference) and `uid` (String) for same relationship

    2. **Users Collection Relationships**:
       - `users.friends[]` → `users/{uid}` (friendships, List<String> or List<DocumentReference>?)
       - `users.friend_requests[]` → `friend_request/{id}` or direct references?
       - `users.home_course` → String (should be `course/{id}` reference?)

    3. **Chats Collection Relationships**:
       - `chats.memberIds[]` → `users/{uid}` (chat members, List<String>)
       - `chats.users[]` → `users/{uid}` (legacy, List<DocumentReference>)
       - `chats.user_a` → `users/{uid}` (direct chat participant, DocumentReference)
       - `chats.user_b` → `users/{uid}` (direct chat participant, DocumentReference)
       - `chats.gameId` → `games/{id}` (String, not DocumentReference - inconsistent)
       - **Subcollection**: messages (parent-child relationship)
       - **Inconsistency alert**: Both `memberIds` (String[]) and `users` (DocumentReference[]) for same data

    4. **Chat Messages Subcollection**:
       - `chats/{chatId}/messages.senderId` → `users/{uid}` (String)
       - `chats/{chatId}/messages.reactions.{userId}` → `users/{uid}` (Map keys as String UIDs)
       - Legacy: `chat_messages.user.id` → `users/{uid}` (deprecated top-level collection)

    5. **Friend Requests Collection**:
       - `friend_request.sender` → `users/{uid}` (DocumentReference or String?)
       - `friend_request.receiver` → `users/{uid}` (DocumentReference or String?)
       - Status field for accept/decline workflow?

    6. **Course Collection Relationships**:
       - No outbound references (lookup table)
       - Referenced by: `games.courseRef`, `users.home_course` (String)

    - Access patterns (how is relationship queried/traversed?)
    - Problem explanation

<task type="auto">
  <name>Task 2: Identify orphaned data risks and cascading operation gaps</name>
  <files>.planning/phases/09-data-model-schema-audit/DATA-RELATIONSHIPS-AUDIT.md</files>
  <action>
    **Audit referential integrity and orphaned data risks:**

    1. **Game Deletion Scenarios**:
       - When game is deleted:
         - `games.chatRef` → orphaned chat? (should chat be deleted too?)
         - `users.{joinedPlayers}` → no back-reference to remove (users don't track joined games)
         - `chats.gameId` → orphaned reference in chat (chat still exists but game is gone)
       - **Check**: Are there soft deletes (status='cancelled') or hard deletes?
       - **Firestore rules**: Line 389 `allow delete: if false` - games can't be deleted (only cancelled)

    2. **User Deletion Scenarios** (GDPR right to deletion):
       - When user is deleted:
         - `games.uid` → orphaned game host (game becomes hostless)
         - `games.joined_players[]` → stale DocumentReference (user no longer exists)
         - `chats.memberIds[]` → orphaned chat member (chat still includes deleted user)
         - `friend_request.sender/receiver` → orphaned request
         - `users.friends[]` → stale friend reference in other users' friend lists
       - **Critical**: No cascading delete logic identified in security rules or Cloud Functions
       - **Check**: Firebase Auth user deletion triggers? Cloud Functions for cleanup?

    3. **Chat Deletion Scenarios**:
       - When chat is deleted:
         - `chats/{chatId}/messages` → orphaned subcollection (Firestore doesn't auto-delete subcollections!)
         - `games.chatRef` → orphaned reference (game references non-existent chat)
       - **Firestore rules**: Line 352 allows chat deletion if user is member
       - **Critical**: Subcollection cleanup is manual, likely bug source

    4. **Friend Request Scenarios**:
       - When request accepted:
         - `friend_request` document deleted?
         - `users.friends[]` updated on both sides?
         - `users.friend_requests[]` updated?
       - **Inconsistency risk**: Multiple places to update, no transaction enforcement

    5. **Course Scenarios**:
       - Course data is static (read-only per Firestore rules line 308)
       - `games.courseRef` safe (courses don't get deleted)
       - `users.home_course` as String - can become stale if course name changes

    **Document orphaned data patterns with:**
    - Pattern ID (R-ORPHAN-001, R-ORPHAN-002...)
    - Scenario description (what action triggers orphan?)
    - Current behavior (what happens to related data?)
    - Orphaned data impact (broken UI, stale data, query errors)
    - Recommended solution:
      - Cascading delete (Cloud Function to cleanup)
      - Soft delete (mark as deleted, filter in queries)
      - Prevent deletion (security rules block delete)
      - Archive pattern (move to deleted_* collection)
    - Priority (Critical if affects data integrity, High if affects UX)
    - Implementation approach (Cloud Function, security rule, client-side transaction)
    - Estimated effort

    **Check for existing Cloud Functions:**
    - `firebase/functions/` directory - are there any cleanup triggers?
    - onCreate/onUpdate/onDelete triggers for cascading operations?
    - Document what exists vs what's missing
  </action>

       - Example format:
         ```
         users
           ← games.userRef (host)
           ← games.joined_players[] (participants)
           ← chats.memberIds[] (chat members)
           ← friend_request.sender/receiver
           ↔ users.friends[] (bidirectional)

         games
           → users (host via userRef + uid)
           → course (via courseRef)
           → chats (via chatRef)
           ← users (participants via joined_players[])

         chats
           → users (via memberIds[], users[], user_a, user_b)
           → games (via gameId String)
           ⊃ messages subcollection
         ```

    3. **Consistency Issues Summary**:
       - Table of DocumentReference vs String UID inconsistencies
       - Recommendation: Standardize on one pattern (DocumentReference preferred for type safety)
       - Migration strategy for existing data

    4. **Orphaned Data Risk Matrix**:
       - High risk: User deletion (no cascading cleanup, GDPR violation risk)
       - Medium risk: Chat deletion (subcollection orphans)
       - Low risk: Game deletion (blocked by security rules)
       - Impact analysis for each scenario

    5. **Cloud Functions Recommendations**:
       - **onDelete(users/{uid})**: Cleanup games, chats, friend_requests, friend lists
       - **onDelete(chats/{chatId})**: Cleanup messages subcollection (critical!)
       - **onUpdate(games/{gameId})**: Sync denormalized data if host/course changes
       - **onUpdate(users/{uid})**: Sync display_name to denormalized fields if changed
       - Priority and estimated effort for each function

    6. **Phase 11 Integrity Roadmap**:
       - Critical fixes (implement before beta):
         1. Chat messages subcollection cleanup function
         2. Standardize gameId → games relationship (String to DocumentReference)
         3. Standardize user relationships (DocumentReference everywhere)
       - High priority fixes (strongly recommended for beta):
         4. User deletion cascade cleanup function
         5. Friend request bidirectional consistency enforcement
         6. Legacy chat migration (users[] → memberIds[])
       - Medium priority (post-beta):
         7. Course reference standardization (String → DocumentReference in users.home_course)
       - Estimated total effort in hours
       - Recommended execution order

    7. **Best Practices Guide**:
       - **Relationship design**:
         - Use DocumentReference for type safety and query flexibility
         - Reserve String UIDs for security rules (request.auth.uid comparisons)
         - Document why each relationship uses its pattern
       - **Referential integrity**:
         - Plan cascading deletes before implementing delete features
         - Use Cloud Functions for cleanup (not client-side, ensures execution)
         - Consider soft deletes (status field) for important entities
         - Always cleanup subcollections (Firestore doesn't auto-delete them)
       - **Bidirectional relationships**:
         - Use transactions for atomic updates on both sides
         - Document which side is source of truth
         - Consider denormalizing only when read:write ratio justifies it
       - **Testing strategies**:
         - Test delete scenarios in integration tests
         - Mock Cloud Functions locally (Firebase emulator)
         - Verify security rules prevent orphaning (block deletes vs cleanup)

    8. **Data Migration Considerations**:
       - Breaking changes: String → DocumentReference requires client code updates
       - Backward compatibility: Support both patterns during transition?
       - Migration script approach: Batch update existing documents
       - Estimated data volume and migration time

    9. **Cross-References**:
       - Phase 8 architectural violations: Direct Firestore access makes cascading ops harder
       - Phase 9 Plan 01 schema audit: Field redundancy (uid + userRef) stems from relationship inconsistency
       - Phase 9 Plan 02 query audit: String UID vs DocumentReference affects query patterns
       - Phase 11 refactoring: Service layer should encapsulate relationship management logic
