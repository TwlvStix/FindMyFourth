<task type="auto">
  <name>Task 1: Audit try-catch patterns and exception handling</name>
  <files>.planning/phases/10-state-management-error-handling-audit/ERROR-HANDLING-AUDIT.md</files>
  <action>
    Analyze exception handling patterns across all code layers:

    1. **Try-Catch Coverage Audit:**
       - Search all try-catch blocks (grep "try\s*\{" with context)
       - Identify async operations without try-catch (await calls outside try blocks)
       - Check for empty catch blocks (anti-pattern)
       - Verify catch blocks add meaningful context before rethrow
       - Identify overly broad catches (catching Exception when specific is better)

    2. **Exception Type Analysis:**
       - Audit FirebaseException handling (specific error codes like permission-denied)
       - Check FirebaseAuthException handling in auth flows
       - Identify generic Exception throws that should be specific types
       - Search for unhandled exception types (PlatformException, FormatException, etc.)

    3. **Layer-Specific Error Handling:**
       - **Service Layer:** Should throw with business context
       - **Provider Layer:** Should catch, log, rethrow with additional context
       - **Widget Layer:** Should catch and display user-friendly messages
       - Identify violations where layers handle errors incorrectly

    4. **Error Propagation Patterns:**
       - Check for swallowed errors (catch without rethrow or user notification)
       - Verify errors bubble up from services → providers → widgets
       - Identify missing error boundaries in StreamBuilder/FutureBuilder
       - Document rethrow patterns with context preservation

    5. **Issue Categorization:**
       For each issue, document:
       - File path and line numbers
       - Current error handling (or lack thereof)
       - Impact (silent failures, poor UX, difficult debugging)
       - Recommended pattern with code example
       - Priority (Critical/High/Medium/Low)
       - Estimated effort (hours)

    **Categories:**
    - E-CATCH-001 through E-CATCH-999: Try-catch coverage gaps
    - E-TYPE-001 through E-TYPE-999: Exception type issues
    - E-LAYER-001 through E-LAYER-999: Layer-specific violations
    - E-PROP-001 through E-PROP-999: Error propagation problems

    Generate ERROR-HANDLING-AUDIT.md with:
    - Executive summary with error handling health score (0-100)
    - Issue count by category and priority
    - Detailed issue list with file paths, code examples, recommendations
    - Layer-specific error handling best practices
  </action>

    - All try-catch patterns audited
    - Exception types analyzed by layer
    - Issues categorized with priorities and effort estimates
  </verify>

    - Error propagation violations identified

       - Audit all SnackBar usage (179 instances found via grep)
       - Check showDialog error modals for consistency
       - Identify ScaffoldMessenger usage patterns
       - Search for setState error flags displayed in UI
       - Document inline error messages in forms vs global notifications

    2. **Error Message Quality:**
       - Review error message text for clarity and actionability
       - Identify technical jargon exposed to users (FirebaseException messages shown raw)
       - Check for hardcoded vs localized error strings
       - Verify error messages suggest next steps ("Try again", "Check connection", etc.)
       - Identify missing error states in loading/success/error UI patterns

    3. **StreamBuilder/FutureBuilder Error States:**
       - Audit 44 StreamBuilder/FutureBuilder instances for error handling
       - Check snapshot.hasError branches exist
       - Verify error UI renders appropriately (not blank screens)
       - Identify missing retry mechanisms in error states
       - Document fallback content for failed loads

    4. **Form Validation vs Runtime Errors:**
       - Distinguish between validation errors (shown inline) and runtime errors (snackbars)
       - Check form field validators exist and are consistent
       - Verify GlobalKey&lt;FormState&gt; error display patterns
       - Identify missing client-side validation before server calls

    5. **Error Recovery Mechanisms:**
       - Search for retry buttons/logic after failures
       - Check for offline-mode handling or connectivity checks
       - Identify timeout handling for long operations
       - Verify users aren't stuck in error states without recovery options
